## ADR-001 — Backend: Python, FastAPI, SQLAlchemy, Alembic

**Status.** Proposed.

**Context.** The owner wants a Python backend serving a separate React frontend. The MVP is a single instance for groups the owner knows: low traffic, one organizer per league, no realtime (PRD §4.2).

**Decision.**

| Concern | Choice |
|---|---|
| Runtime and tooling | Python 3.15, `uv` for environments, the lock file and scripts |
| Web framework | FastAPI on uvicorn |
| Schemas | Pydantic v2; request and response models form the API contract (ADR-008) |
| Database access | SQLAlchemy 2.1 with typed `Mapped[]` models, **synchronous** sessions, psycopg 3 driver |
| Migrations | Alembic, one linear history; autogenerate is only a draft and every migration is reviewed |
| Transactions | The request owns the transaction: one per request, opened by a `yield` dependency that commits before the response is sent, or rolls back on an error (`Depends(scope="function")`, FastAPI 0.121 or later). One exception: the refresh endpoint returns its 401 for a reused token instead of raising it, so that the revocation of the token's family commits (ADR-006). Services never commit (`docs/style/python-style.md` §5) |
| Settings | pydantic-settings, environment variables with the prefix `TOURNEYHUB_`; startup fails on missing or invalid config |
| Password hashing | argon2-cffi (Argon2id) |

**Consequences.**
- Endpoints are plain `def` functions; FastAPI runs them in its thread pool. With the MVP's load this is more than enough, and it avoids async ORM pitfalls (lazy loads across awaits, session sharing).
- A failed commit reaches the error handlers, so the client gets an error instead of a 2xx. With FastAPI's default scope, the code after `yield` runs after the response has been sent, and a commit could fail after the client had received a 2xx.
- Moving to async later is possible endpoint by endpoint if realtime (RM-03) needs it.

**Alternatives considered.** Django with Django Ninja (auth, admin and migrations built in; the owner chose FastAPI, and the admin surface is two screens). Litestar (smaller ecosystem). Async SQLAlchemy with asyncpg (no benefit at MVP load, more complexity).

## ADR-002 — Database: PostgreSQL

**Status.** Proposed.

**Context.** The data is strongly relational (leagues, seasons, tournaments, entries, matches) and must be the same in development and production.

**Decision.**
- PostgreSQL 17, run as a container in Docker Compose locally and on the VPS.
- The database is created with PostgreSQL 17's built-in locale provider, `--locale-provider=builtin --builtin-locale=C.UTF-8`, passed to the image as `POSTGRES_INITDB_ARGS`. `lower()` then folds Czech letters (`Č` to `č`) by Unicode case mapping, and the `lower()` indexes do not depend on the image's glibc version, which can otherwise change under them with a base-image upgrade. A database created with the plain `C` locale would not fold `Č` at all.

**Consequences.**
- Constraints are enforced in the database where they can be: at most one active season per league via a partial unique index. Primary keys are UUIDv7 values generated by the application, for leagues and tournaments by the client (ADR-008).
- Player names are unique per league ignoring case (BR-001) via a unique index on `(league_id, lower(name))` that **includes removed players**, so two different people never share a name in past results. When the organizer adds a name that belongs to a removed player, the API refuses the add (422 `player_name_taken`, with the holder's `player_id` and `removed: true`, ADR-008) and the app asks whether it is the same person. If it is, the app restores that player with their history (`PUT …/players/{id}/removed` with `removed: false`); if not, the organizer must choose a different name, so a newcomer never takes over someone else's record. FR-012 states this rule (#48).
- Text sorts by code point. A list that must be in Czech order uses `COLLATE "cs-x-icu"` in SQL or `Intl.Collator('cs')` in the UI.
- The locale's behaviour is stable within a PostgreSQL major version, so the release notes are checked before a major upgrade. A test checks the folding.

**Alternatives considered.** SQLite (simpler operation, but would need a migration to PostgreSQL once the roadmap's later stages arrive). The image's default `en_US.utf8` locale (folds Czech letters too, but ties the indexes to glibc).

## ADR-003 — Frontend: React, Vite, TypeScript, Tailwind, shadcn/ui

**Status.** Proposed.

**Context.** Every screen must work on a phone, and entering a result takes at most three taps (FR-082). The UI is in English and Czech (FR-080, FR-081). The design is in [Figma](https://www.figma.com/design/Vqxx2eyO6oNaLprB9wewHo/TourneyHub): every screen has a phone, a tablet and a desktop layout, each in a light and a dark theme.

**Decision.**

| Concern | Choice |
|---|---|
| Framework and build | React 19, Vite, TypeScript in strict mode |
| Styling and components | Tailwind CSS, shadcn/ui (Radix-based components copied into the project) |
| Layout | Mobile-first: every screen is built for the phone first, and Tailwind's breakpoint prefixes add the tablet and desktop layouts the design shows; nothing is designed for the desktop and squeezed down. The phone is the reference for FR-082 |
| Server state | TanStack Query |
| Routing | React Router |
| Translations | react-i18next; no hard-coded user-facing strings; dates formatted with `Intl` in the chosen language |
| Remembered language (FR-081) | Organizers: a field on their account (`users.language`). Viewers: the browser's language if it is English or Czech, otherwise English; a viewer's own choice is kept in `localStorage` |
| Themes | A light and a dark theme for every screen, as the design in Figma has them; the theme follows the device's setting (`prefers-color-scheme`). Colours come from theme tokens (Tailwind and shadcn/ui CSS variables), never from hard-coded values; their values are the Figma variables, and a colour the design lacks (destructive, focus ring, charts) is added with its WCAG 2.2 AA contrast ratios recorded (`docs/style/frontend-style.md` §5.2) |
| Fonts | The design's Atkinson Hyperlegible Next and Big Shoulders, self-hosted from the `@fontsource` packages, since the CSP allows only `'self'`; only the weights and the Latin subsets the UI uses |
| Demo mode | `pnpm dev:demo` runs the app against a fake API in the browser (Mock Service Worker, a dev dependency), so screens can be built and shown before their backend routes exist. A production build contains none of it |
| API types | Generated at build time from the committed OpenAPI schema with `openapi-typescript`; `openapi-fetch` is the runtime client they type (ADR-008) |
| Node.js | The current Active LTS (26 from 2026-10-28), pinned in `.nvmrc` and `engines` |
| Package manager | pnpm, its version pinned in the `packageManager` field; `pnpm-lock.yaml` committed |

**Consequences.**
- The knockout options keep their English names in both languages (FR-080).
- Demo mode needs a provisional contract for routes the backend lacks (ADR-008). Its handlers also serve the Vitest tests, so the demo and the tests share one fake API; it is replaced route by route as the backend grows.
- Both themes ship in the MVP, as the design has them. Every screen and component is built and checked in both, which costs more than one theme; tokens keep that cost to the colours, not the layout. A manual theme switch is not in the MVP.
- pnpm keeps `node_modules` strict: code can import only what its own `package.json` declares.
- pnpm does not run dependency install scripts unless the package is on an allow-list (`allowBuilds` in `pnpm-workspace.yaml`). An unlisted install script fails `pnpm install`, so the list is reviewed like code. Today it lets no package run one, and it denies `@swc/core`'s explicitly.
- Node 25 and later no longer ship Corepack, so pnpm is installed explicitly: in CI with `pnpm/action-setup`, which reads the pinned version, before `actions/setup-node` with `cache: pnpm`, then `pnpm install --frozen-lockfile`; in the Dockerfile with the same pinned version. Playwright browsers are installed with `pnpm exec playwright install`; `--with-deps` adds the system packages where the machine lacks them (CI's runner image has them).

**Alternatives considered.** Mantine (faster start, less control over the look). Plain Tailwind (most work, accessibility of dialogs and menus on us). npm (nothing extra to set up, but `node_modules` is not strict and dependency install scripts run by default).

## ADR-004 — Repository layout and local development in Docker

**Status.** Proposed.

**Context.** Development happens locally first; deployment to the VPS comes in a later MVP phase (ADR-014). The app must also be tried on a real phone during development (FR-082).

**Decision.**
- One repository with `backend/` (Python package `tourneyhub`) and `frontend/` (the React app).
- Three Compose files at the root. `compose.yaml` holds what every setup shares: `db` (PostgreSQL), the internal network with a fixed address range (ADR-006) and the volumes. `compose.override.yaml` holds the development services and is loaded automatically by `docker compose`. `compose.prod.yaml` holds the production images and is used for end-to-end tests (ADR-013) and on the VPS (ADR-014), selected with `COMPOSE_FILE=compose.yaml:compose.prod.yaml` in `.env` or with explicit `-f` flags. One file cannot hold both: Compose allows one definition per service name, and profiles only switch services on and off.
- Development services: `api` (uvicorn with reload, source mounted) and `frontend` (Vite dev server with hot reload, `node_modules` in a named volume because the macOS host and the Linux container need different native binaries). Vite proxies `/api` to `api`, so the browser sees one origin, as in production (ADR-005).
- The development stack runs over plain HTTP, on `http://localhost` and on the machine's LAN address for a phone. Browsers do not keep `Secure` cookies there (Safari not even on `localhost`), so `TOURNEYHUB_COOKIE_SECURE=false` switches the refresh cookie's `Secure` attribute off. `TOURNEYHUB_ENV` is `development` or `production`, and the API refuses to start with `TOURNEYHUB_COOKIE_SECURE=false` unless `TOURNEYHUB_ENV=development`.
- `compose.prod.yaml` runs the images that go to the VPS: `api`, and `web` (Caddy serving the built frontend and proxying `/api`). Locally, Caddy serves HTTPS with its internal certificate authority (`tls internal`), and Playwright runs with `ignoreHTTPSErrors`, so the `Secure` cookie works in every browser, including WebKit.
- Alembic migrations run when the `api` container starts. A CLI entry point `tourneyhub` hosts admin and maintenance commands (ADR-007).
- Configuration comes from a `.env` file; `.env.example` is committed, `.env` is not.

**Consequences.** `docker compose up` gives a working development app. `docker compose -f compose.yaml -f compose.prod.yaml up` runs exactly the images that the VPS will run; the development services do not.

**Alternatives considered.** One HTTPS origin in development too, with Caddy and `tls internal` in front of Vite (removes the toggle, but every developer machine and every test phone must trust Caddy's root certificate). Distinct service names for development and production in one file (works, but the VPS would carry the development definitions).

## ADR-005 — One origin behind Caddy

**Status.** Proposed.

**Context.** Splitting the frontend and API across domains would need CORS and cross-site cookies.

**Decision.** In production, Caddy is the only public entry point. It obtains HTTPS certificates automatically (Let's Encrypt), serves the built frontend on `/` (falling back to `index.html` for client-side routes) and proxies `/api/*` to the `api` container.

Caddy adds three headers to every response: a Content-Security-Policy that allows only the app's own origin, plus inline styles (Radix UI injects them) and `data:` images, and forbids framing; `X-Content-Type-Options: nosniff`; and `Referrer-Policy: same-origin`, so a share token in an address (ADR-008) never reaches another site. `Strict-Transport-Security` is switched on in the deployment phase (ADR-014).

**Consequences.** No CORS configuration. The refresh cookie (ADR-006) is first-party. Only Caddy's ports 80 and 443 are exposed; `api` and `db` are reachable only on the internal Docker network.

**Alternatives considered.** Nginx with certbot (more configuration, separate certificate renewal). Separate domains for app and API (CORS and cookie scoping without benefit).

## ADR-006 — Authentication: JWT access token and rotating refresh token

**Status.** Proposed.

**Context.** Organizers stay logged in on a device until they log out (FR-003). Only the organizer and admin screens need authentication; viewers use the share link (FR-070). Organizers mostly use phones, often on a weak connection, and may have the app open in several tabs.

**Decision.**
- **Passwords:** 15 to 1024 characters, counted as characters, not bytes (FR-002, decided in #48). 15 is what NIST SP 800-63B-4 requires for a password used alone; 1024 stays well above any password manager's length and bounds the work of hashing. The MVP checks no list of common or breached passwords (FR-002, decided in #48). Sign-up, password change and an admin's temporary password share one rule, kept in one place. Passwords are hashed with Argon2id and rehashed on login when the parameters change. Email addresses are compared case-insensitively and are unique.
- **Hashing load:** argon2-cffi's default parameters use 64 MiB per hash. Every hash and verification runs under one process-wide bounded semaphore of 4, so a burst of logins needs at most 4 × 64 MiB = 256 MiB instead of about 2.5 GiB for FastAPI's 40 threads, and the VPS is not sized for Argon2 (`docs/style/python-style.md` §10).
- **Access token:** JWT signed with HS256, valid 15 minutes, carrying the user id and the refresh-token family id. The SPA keeps it in memory only and sends it as `Authorization: Bearer`. Authorization does not rely on claims that can change: on every request the server reads `is_admin` and `must_change_password` from the user row, in the lookup the request needs anyway.
- **Refresh token:** an opaque 256-bit random value, stored only as a SHA-256 hash, sent as an `HttpOnly; Secure; SameSite=Strict` cookie restricted to the path `/api/v1/auth`. Every refresh issues a new token and marks the presented one as rotated; each token records the token it was rotated from. The refresh endpoint locks the family's rows (`SELECT … FOR UPDATE`) before reading them, so presentations within one family are handled one at a time. The presented token decides the outcome:
  - revoked or expired: 401, nothing else changes;
  - not yet rotated: a normal rotation, which also revokes its unrotated siblings (tokens of the same family rotated from the same parent), the extra tokens a reissue in the window below leaves behind;
  - rotated less than 60 seconds ago: another new token in the same family, and its rotation time stays unchanged; this covers two tabs refreshing at the same moment and an immediate retry after a lost response;
  - rotated earlier: reuse of an invalidated token, which revokes the whole family (theft detection).
- **Limits of the 60-second window, accepted:** a lost response retried after more than 60 seconds logs the user out. A token stolen and used within the window before the legitimate client creates a second branch; the next normal rotation keeps whichever holder refreshes first, so if the thief is first, the organizer is logged out without an alarm. Only hashes are stored, so an earlier replacement cannot be sent again.
- **Staying logged in:** refresh tokens expire after 90 days without use, and each refresh restarts that period. An organizer who uses the app stays logged in until they log out; a forgotten device loses access after 90 days, which still covers a league's summer break. FR-003 states the 90 days (proposed in #48). Expired rows are deleted regularly, and so are revoked ones, which answer like an unknown token; rotated rows stay until they expire, because reuse detection needs them. `tourneyhub cleanup` does it; a schedule comes with deployment.
- **Revocation:** logout revokes the current family. A password change revokes every other family of that user and keeps the one it came from. It needs the current password, and the new one must differ from it, so that the password an admin reset gave does not survive the reset. A wrong current password is 422 `wrong_password`, never 401, which would make the SPA refresh and retry. The check spends the login's budget (see Abuse limits), because someone with a stolen token could otherwise guess the password without limit. A login that verified the old password while a change committed is refused. An admin password reset revokes all of the user's families. FR-004 and FR-006 state it (proposed in #48), and the UI says that changing the password logs out the other devices.
- **Password change after an admin reset:** an admin reset (FR-006) sets `users.must_change_password`, and the organizer's next password change clears it. Until then login succeeds, but every route except `/api/v1/auth/*` and `GET /api/v1/me` returns 403 with the code `password_change_required`, and the frontend opens the new-password screen. The admin therefore knows an organizer's password only until their next login. FR-006 states this rule (proposed in #48).
- **CSRF:** API calls authenticate with the Bearer header, which a browser never adds by itself. The refresh and logout endpoints, which rely on the cookie, also require a custom request header that cross-site forms cannot send.
- **Abuse limits:** login attempts are limited per email address and per client IP, and sign-up attempts per client IP, to stop guessing passwords and the sign-up code. Counters live in PostgreSQL (`auth_attempts`), so no Redis is needed, and rows older than the longest window are deleted by `tourneyhub cleanup`. Each attempt is counted before its password is checked, so parallel attempts count each other. Repeated failures open a growing waiting period instead of locking the account, so nobody can lock an organizer out on a tournament evening by knowing their email: an attempt inside it gets 429 `too_many_attempts` with `Retry-After` in seconds, is not counted and never reaches the password check. No request sleeps in the server's thread pool. The client IP comes from `X-Forwarded-For`, trusted only from Caddy: uvicorn's `FORWARDED_ALLOW_IPS` is set in `compose.prod.yaml` to the internal Docker network's address range (`COMPOSE_SUBNET` in both Compose files, default `172.30.0.0/24`, so the two cannot drift), since by default it trusts only `127.0.0.1` and `::1` and every request would carry Caddy's address. IPv6 addresses are counted per /64. Logins get 3 free failures in 15 minutes, then a waiting period that doubles from 1 s up to 8 s. Sign-up has no Argon2 to slow a guesser down, so it gets 5 free failures in an hour, then a period that doubles up to 15 minutes. A password change counts on the login's budget, per email and per client IP, so failures at login and at password change add up. A request whose body fails validation is refused before it is counted.

**Consequences.** The SPA refreshes on page load and when a request gets 401, with at most one refresh in flight per tab; requests that get 401 meanwhile wait for it and are retried once. A 403 never triggers a refresh (ADR-008). A revoked login cannot be refreshed, and the API checks the token's family on every request, with one indexed lookup (a partial index on `refresh_tokens.family_id` where `revoked_at` is null): after a reset, a logout or a password change elsewhere the access token stops at once, not after up to 15 minutes. The answer is 401 `token_expired`, so the SPA refreshes once, fails and logs out. The token design also suits a future phone app (RM-19) and Google sign-in (RM-20).

**Alternatives considered.** A server-side session cookie (simpler, immediate revocation, no rotation; the reviewer recommended it, the owner keeps JWT). A rotated token that stays valid until one of its successors is used, instead of the 60-second window (also covers late retries after a lost response, at the cost of more state to check). Long-lived JWTs without refresh (no revocation).

## ADR-007 — Instance admin: admin flag, admin screens, CLI bootstrap

**Status.** Proposed.

**Context.** The instance admin sets the sign-up code (FR-005) and sets a new password for an organizer who forgot theirs (FR-006). There is one instance and usually one admin, the person running the VPS.

**Decision.**
- The admin is a normal account with an `is_admin` flag. An admin can also be an organizer with their own leagues. The server checks the flag in the database on every admin request, never from the access token (ADR-006).
- The admin section in the React app lets an admin set or change the sign-up code, list organizer accounts and set a new password for one, which revokes their logins and makes them choose a new password at their next login (ADR-006). Every admin action is checked on the server and recorded with who did it and when.
- The first admin is created on the server with a one-off CLI command, e.g. `docker compose exec api tourneyhub create-admin --email …`, which prompts for the password. The same CLI can grant the flag to an existing account and revoke it. No web route can create an admin, so a stranger cannot claim the instance on first start.
- Until a sign-up code is set, sign-up is closed. Changing the code does not affect existing accounts (FR-005). A wrong code and a closed sign-up get the same answer, 422 `invalid_signup_code`, and the code is checked before the email, so that a stranger learns no email address. The CLI command `tourneyhub set-signup-code` reads the code from a prompt, or closes sign-up with `--clear`, so sign-up works before the admin screens exist. The code has 12 to 256 characters, compared after Unicode normalization (NFC) and with surrounding whitespace stripped; `--generate` makes a random one and prints it once, as the only output. The code itself is never recorded in `admin_actions`; a change of it is, from the web and from the CLI alike (below, DATA-MODEL §4.1).
- The admin routes are under `/api/v1/admin`: the sign-up code (read, set or clear, generate), the list of accounts and the password reset. One dependency on their router checks the flag in the database, so a route cannot be added without the check. A response that holds a code or a password is sent with `Cache-Control: no-store`.
- A password reset takes a temporary password the admin chose, under the same length rule as every password, or has the server generate one with `secrets`. A generated password is in the response once; it is neither stored in clear nor recorded, and the screen drops it when it is closed. The admin cannot reset their own account (422 `own_account`): the reset would end their own login; they change their password as everyone does. The web reset also refuses an admin's account (422 `admin_target`): a stolen admin session could otherwise take over every other admin, so an admin's password is handled with the CLI, as the admin flag is. Any organizer account can be reset.
- `admin_actions` records the changes, not the reads: setting, generating or clearing the code (`set_signup_code`, one action for all three), a reset (`reset_password`) and the CLI's `create_admin`, `grant_admin` and `revoke_admin`; the row holds the source, the admin, the target and the time, never the code or a password. Nothing is recorded when nothing changes: `grant-admin` for an admin, `revoke-admin` for a non-admin, closing a sign-up that is already closed, or setting the code it already has. The `set-signup-code` command records `set_signup_code` with source `cli`. The CLI's `create-admin` applies the same display-name rules as the API: NFC, 1 to 100 characters after stripping, whitespace collapsed, no invisible or look-alike characters.
- Admin rights do not give access to other organizers' leagues (FR-007).

**Consequences.** Granting or revoking admin rights takes effect on the next request. The admin knows an organizer's password only between a reset and the organizer's next login. Admin actions from the CLI and from the web are recorded in the same place, distinguished by their source.

**Alternatives considered.** CLI-only administration (smallest attack surface, less comfortable). A sign-up code in an environment variable (a code change needs a restart).

## ADR-008 — API conventions and generated client types

**Status.** Proposed.

**Context.** The API serves one SPA written by the same team, and possibly a phone app later (RM-19). A league has one organizer, but they may use several devices, mostly a phone on an unreliable connection, so requests get retried and screens go stale.

**Decision.**
- REST with JSON under `/api/v1`. The share-link views are anonymous, read-only routes under `/api/v1/public/{share_token}/…` (FR-070–FR-072): `GET /api/v1/public/{share_token}` (the league's name, its seasons and its players, removed ones included), `GET …/seasons/{season_id}/tournaments` (without the tournaments in setup), `GET …/tournaments/{tournament_id}` (the organizer's whole-tournament view), `GET …/seasons/{season_id}/standings` (the season standings), `GET …/tournaments/{tournament_id}/standings` (a round robin's standings now, without the organizer's form and tie-break notes) and `GET …/tournaments/{tournament_id}/places` (the places and season points). Their response models list only what viewers may see: no league id, owner, email, share token, draw counter or lot seed. An unknown token, a malformed one and a deleted league's are 404 `share_link_not_found` with an empty `detail` on every route, after one lookup on the unique index of `share_token`; a tournament in setup is 404 `tournament_not_found`, the same answer as an unknown one or one of another league, and another league's season is 404 `season_not_found`. Every answer under `/api/v1/public`, errors included, carries `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; behind Caddy it also carries ADR-005's `same-origin`, and a browser applies the last policy it knows, `no-referrer`. Sign-up, login, refresh and logout under `/api/v1/auth`, and every route under `/api/v1/public`, work without an access token; every other route requires one.
- Every error returns an HTTP status and a body `{"code": "<stable_code>", "detail": {…}}`, including the framework's own errors: custom handlers for `RequestValidationError` and `starlette.exceptions.HTTPException` (which also covers the router's 404 and 405) replace FastAPI's defaults, which return `detail` as an English string or a list. Their codes are `validation_failed` (422), `not_found` and `method_not_allowed` (the router's 404 and 405), `bad_request` (any other HTTP error) and `internal_error` (500, any unexpected error). The error schema is declared in OpenAPI with `code` as an enum, so the generated types know it. `detail` carries structured parameters, for example `{"min": 4, "given": 3}`, from which the frontend builds English or Czech messages; the backend never returns user-facing text.
- Status codes the frontend acts on: 401 (`not_authenticated`, `token_expired`) makes it refresh once and retry once (ADR-006); 403 (`forbidden`, `password_change_required`) never does; 409 makes it reload the state; 422 makes it show a message built from the code and `detail`; 404 on a repeated delete means the delete already happened; 429 (`too_many_attempts`, a throttled login, sign-up or password change, with `{"retry_after": <seconds>}` in `detail` and the same value in `Retry-After`) makes it show the wait, not a generic error, and never retry automatically (ADR-006).
- 409 is used only when the request carried an expectation that is stale and a reload repairs it: an expected value, a target state, the client id of another row. The reloaded screen shows what changed. 422 with a stable code (`RuleViolationError` in the backend) means that the current state refuses the request and the organizer needs a message, for example a player name the league already has (BR-001), an email that already has an account (FR-002) or too few entries; a reload would change nothing. Services check these rules under the lock (`docs/style/python-style.md` §4.4). The exception is a race the lock cannot cover: of two parallel sign-ups with one email, the one that loses the unique index gets 409 with the same code `email_taken`; a player name that a write without the league lock takes first gets 409 `player_name_taken` the same way, and one tournament id sent to two leagues of one organizer at once, whose league locks do not exclude each other, gets 409 `tournament_id_taken` from the primary key. `player_name_taken` carries the holder's `player_id`, `name` and `removed`, so that the UI can offer to restore a removed holder (ADR-002); a league holds at most 1000 active players, removed ones not counted, and an add or a restore over that is 422 `player_limit_reached` (detail: `limit`; BR-006, proposed in #48, the code still counts 500 including removed players); a removed player can be renamed, as BR-011 says a rename always applies, and the new name is checked like any other; a player's id from another league is 404 `player_not_found`. A write to a closed season (BR-011), such as a change to its placement points table, is 409 `season_closed`: the UI shows closed seasons read-only, so only a stale screen sends one, and the reloaded screen shows the season closed. Renaming a closed season, which BR-011 allows, is not refused. Deleting a tournament of a closed season is 409 `season_closed` the same way (FR-038). In tournament setup, a stale screen gets 409: `tournament_not_in_setup` (the tournament has started), `tournament_type_changed` (a write meant for another type, such as pairs for Singles), `player_not_picked` (a pair or a half names a player who is no longer picked), `draw_counter_changed` (with the current `draw_counter`), `seeding_method_changed` (a shuffle of seeds that come from the ranking), `seed_order_changed` and `player_removed` (a removed player is picked: the player list changed after the screen loaded); an unknown tournament or one of another league is 404 `tournament_not_found`. In the whole-format write, `sit_out_points` (FR-039, BR-071, BR-075) is for a Swiss or Monster DYP group phase: 0, 1 or 2 is stored as given, and null or a missing value stores the default, 0; the default does not depend on the match format or the league's draw setting. A round robin has none: a number there is 422 `sit_out_points_not_applicable` (in a complete round robin every entry sits out equally often, and with a late entry (BR-054) the points would distort the order); a change from Swiss to a round robin drops the value, and one back starts from 0. The read returns the value, null for a round robin. The value cannot change while the phase has a result (BR-075, BR-096): the format write is 409 `tournament_not_in_setup` once the tournament has started. Any other number is 422 `validation_failed`. The 422 codes of setup are `draws_not_allowed` (BO2 in a league without draws, BR-121), `sit_out_points_not_applicable` (points for sitting out in a round robin, BR-071), `nothing_to_pair` ("pair the rest" in Doubles with fewer than two players without a partner, FR-033), `dyp_halves_incomplete`, `dyp_halves_unequal`, `too_many_left_out` and `not_enough_players` (a new DYP draw, BR-031, BR-032). "Generate and start" (FR-035) carries the expected draw counter: a started tournament is 409 `tournament_not_in_setup`, a stale counter 409 `draw_counter_changed`; an incomplete setup is 422 `players_without_partner` (a Doubles player without a pair, detail `unpaired`), `not_enough_entries` (FR-032, detail `minimum` and `given`), `too_many_entries_for_round_robin` (a round robin of more than 16 entries, FR-032, decided in #48; the code still stops at 64; detail `limit`) or one of the DYP draw's codes, and a format whose rounds the backend does not generate yet is 422 `format_not_supported` (detail `format`) until it does. "Back to setup" (FR-036) carries the state it expects, `in_progress`: any other state is 409 `tournament_not_in_progress`, and a tournament with a result is 422 `tournament_has_results` (detail `results`). A result (FR-050 to FR-053) is `PUT …/matches/{match_id}/result` with the whole result; the empty result, with no walkover and no games, clears it, so clearing is a target state like any other and needs no `DELETE`. An unknown match or one of another tournament is 404 `match_not_found`; a result in a closed season is 409 `season_closed`; the 422 codes of a result are `match_sides_unknown` (BR-091), `result_does_not_fit_format` (BR-121, detail `format` and `games`), `draws_not_allowed` (BR-090, the code BO2 already uses in setup), `game_score_mismatch` and `scores_required` (BR-092, detail `game_no`). Finishing a round robin without a knockout (FR-040) carries the state it expects, `in_progress`: any other state is 409 `tournament_not_in_progress`, a match without a result 422 `group_phase_not_done` (detail `matches_left`). The running group phase's waiting list and standings are one read, `GET …/play`; there is no separate tournament standings route for the organizer. The season's standings are `GET …/seasons/{season_id}/standings`, computed from the season's finished tournaments with its placement points table (BR-112, BR-113): every player who played in one, removed players too (BR-002), and an empty list for a season with none; another league's season is 404 `season_not_found`. What one finished tournament changed in them is `GET …/tournaments/{tournament_id}/season-effect`: the standings with the tournament next to the standings of the season's other finished tournaments. A tournament that is not finished has no places and no effect, so the list is empty. Fields while the tournament runs (FR-090 to FR-094) are `POST …/fields` with the number the new field expects, `DELETE …/fields/{field_id}` and `PUT …/fields/placements` with the target placement of one match, or of two for a swap; in setup or once finished all three are 409 `tournament_not_in_progress`, since setup sets the number of fields with the format. A stale expected number is 409 `field_number_changed` (detail `number`, the number a new field would get now, null when all 32 are taken); an unknown field or a repeated delete is 404 `field_not_found`, an unknown match 404 `match_not_found`; the last field is 422 `last_field` (BR-132). A placement that names a match with a result is 409 `match_has_result`, and one onto a field that holds a match the request does not name is 409 `field_not_free` (detail `field_id` and `match_id`): the screen offers neither, so only a stale one sends them. A side not known is 422 `match_sides_unknown`, and a player who would be on two fields at once 422 `player_on_another_field` (BR-131, detail `player_ids` and `field_ids`). A picked player of a tournament that is not finished cannot be removed, 422 `player_in_unfinished_tournament` (BR-002), and a season with such a tournament cannot end, 422 `season_has_unfinished_tournaments` (BR-010); turning draws off while the league has an unfinished tournament whose group phase plays BO2 is 422 `draws_needed_by_bo2` (BR-125, BR-013); all three carry the tournaments' ids.
- The OpenAPI schema is generated by FastAPI, exported to `backend/openapi.json` and committed. CI fails if the committed schema differs from the code. The frontend generates its TypeScript types from that file at build time and does not commit them, so this one drift check covers both sides; hand-written copies of API types are not allowed. The one exception is the demo mode's provisional contract (ADR-003): types for routes the backend does not serve yet, written in the generated shape and deleted route by route once `openapi.json` has them. Calls to those routes go through a second client, `provisionalApi`, typed by the generated paths plus the contract and built by the same factory as the main client, so it carries the same authentication; a route moves to the main client once it is generated, and a type check fails while the contract still declares a method the generated schema has. The frontend calls the API only through `openapi-fetch`, typed by these generated types, behind one client module that turns every non-2xx response into an error carrying the status, `code` and `detail`.
- Share tokens are at least 128 bits of randomness, URL-safe (FR-071).
- Every mutating operation inside a league locks the league row first and then, if it touches a tournament, the tournament row (`SELECT … FOR UPDATE`). Two devices of the same organizer cannot interleave changes such as generating a round while entering a result, and the fixed order rules out deadlocks. Rules spanning a league, a season and its tournaments hold: clearing a result in a finished tournament cannot race starting a new season (BR-010, BR-011, BR-095), creating a tournament cannot race closing the season, and removing a player cannot race adding them as a late entry (BR-002).
- Every id in a request (entry, round, match, player) is loaded through the league and tournament the operation locked, so an id from another tournament or another organizer's league is not found.
- Operations that are unsafe to repeat carry the state they expect, checked under the lock; a mismatch returns 409 with a stable code, and the frontend reloads the state instead of showing an error. This covers a retried request whose response was lost and a stale screen on a second device. A round is deleted by its id, never as "the newest round"; adding a round carries the expected round number; starting a season carries the current season's number; "shuffle again", "new DYP draw" and "generate and start" carry the expected draw counter; "back to setup" and finishing a round robin carry the state they expect. Other operations send the target state (`disabled: true`, `removed: true`, a player's new name, the full seed order, the whole format of a tournament in setup, its picked players, its Doubles pairs and its hand-set DYP halves), never a toggle or a relative move; a seed order that does not list exactly the current entries gets 409. A repeated delete by id gets 404, which the frontend treats like a 409.
- A result is sent whole, every game or the walkover, never one game at a time. Field operations send the target placement: a match on a field, or waiting, with the field the screen saw it on (`from_field_id`, null for waiting). If the match is elsewhere now, the answer is 409 `placement_changed`, so a repeat or a move planned from a stale screen changes nothing. Exactly five operations are allowed (FR-093, BR-136): a waiting match on a free field, a match from its field to a free field, a match back to waiting, which holds it, the release of a held match (the target is waiting and not held; a match that is not held now is 409 `placement_changed`), and a swap of two matches that are both on fields (both matches named, each with the other's field). Anything else is 422 `placement_not_allowed`, replacing the match on a busy field and a rotation included, until the PRD decides whether they should exist. Adding a field carries the number it expects to get, and a field is removed by its id (DATA-MODEL §2, §4.6).
- Creating a league or a tournament takes a UUIDv7 generated by the client. A repeated request finds the existing row and gets it back only if it belongs to the same organizer, has the same parent and, for a tournament, the same type; otherwise 409. The id is looked up before any rule of the create is checked, so a retry never gets a 422 that its own first attempt caused. The timestamp inside a client-supplied id is not trusted.

**Consequences.** All writes in a league are serialized; with one organizer per league there is no noticeable waiting. A retried or stale request either changes nothing or gets 409 and reloads. Share tokens appear in every public path. The api's log handler writes each `/public/<token>` as `/public/***`, in uvicorn's access log and every other record. Caddy has no access log, but its default logger writes an error with the whole request when it cannot proxy one (a 502 while the api is down); with Caddy 2.11 that line held the uri, token included (verified). The Caddyfile now replaces the token with `***` in the logged `uri` and `Referer` header (a call from a share page carries the page's address), and the 502 line shows `/api/v1/public/***/…` (verified). Retention, and redaction if Caddy's access log is ever switched on, are decided with the logging in ADR-014.

**Alternatives considered.** Hand-written OpenAPI first (doubles the work with FastAPI). A hand-written fetch wrapper (would restate the paths and parameters the schema already types). GraphQL (no need for the MVP's fixed set of views). Idempotency keys for every mutation (a stored table of keys and responses; expected-state checks cover the same retries and stale screens without it).

## ADR-009 — Tournament engine as pure functions; derived data computed on read

**Status.** Proposed.

**Context.** Most of the PRD's complexity is in the business rules (§7): brackets, schedules, Swiss and Monster DYP rounds, tie-breakers, places and season points. The data is small. FR-032 caps a round robin at 16 entries and sets no maximum for the other formats, but any technical limit must still allow 256 entries and 20 group-phase rounds per tournament, so the design is sized for those numbers; a season has a few dozen tournaments.

**Decision.**
- The engine is a separate package, `tourneyhub.engine`, made of pure functions over immutable data classes. It does not touch the database, the clock or the network, and has no randomness other than the seed it is given (ADR-010). An import-linter contract enforces that it imports nothing from FastAPI, SQLAlchemy or the rest of the app.
- **Stored:** what the organizer decided or what a draw produced: leagues, players, seasons and their placement points tables, tournaments with their settings and their state, entries and pairs with their current disabled flag, seeds, top players marked by the organizer (their order comes from the league ranking; nothing else about top players is stored), rounds, matches, results and seeds for lots.
- **Tournament state is stored:** setup, in progress or finished. The last knockout result finishes a tournament with a knockout (FR-037); the organizer finishes one without (FR-040). Clearing a result puts a finished tournament back in progress (BR-095). The state decides whether a new season can start (BR-010) and which tournaments count for the season (§7.14).
- **Per-round participation is stored.** For every round of a group phase, each entry has a record of whether it played, sat out, was disabled, or had not joined yet. A current "disabled" flag alone is not enough: sit-out counts (BR-058, BR-063), sit-out points of a Swiss or Monster DYP phase (BR-071, BR-076, BR-077) and the rule that missed rounds of disabled and late players earn no points for sitting out but count as sit-outs for the sit-out order only (BR-064, BR-067) all depend on why an entry did not play in each past round.
- **Field assignments are stored; the waiting list is computed.** Which match is on which field depends on the order of events: results entered, fields added and removed, matches placed by hand (BR-130–BR-134). Recomputing it on read would need a log of those events and would move a match being played whenever an earlier result is corrected. A pure engine function returns the placements for the free fields, and the application stores them in the same transaction as the event (DATA-MODEL D10). The waiting list (FR-092) is computed on read.
- **Computed on every read:** tournament standings, BH1, BH2, score difference, places, season standings, the league ranking and the waiting list for fields. The application loads the stored data, calls the engine and returns the result.
- Generating a bracket, a schedule or a round calls the engine and stores the resulting matches.
- The engine marks every outcome that a lot decided (a sit-out, the pairing order, the knockout cut and seeding, a DYP partner, the left-out player), so the UI can show it as decided by lot. Nothing extra is stored, since every lot can be recomputed from the stored seed.

**Consequences.**
- Derived data can never get out of step with results. Corrections (BR-112), placement table changes (BR-012) and deleted tournaments need no recalculation step.
- The placement points table is stored only on seasons. The league settings screen edits the active season's table, a new season starts with a copy of the previous season's table, and a closed season's table no longer changes (BR-012). FR-011 can keep calling it a league setting.
- Engine rules are tested directly, without a database, with test names referring to BR IDs.
- If a page gets slow, caching can be added later without changing the engine. Guidelines for when to act: the standings of a 256-entry tournament in under 200 ms, and the season page with 40 tournaments of realistic size in under 500 ms, measured end to end through the API, because loading the matches costs more than the engine (40 recomputations of a 256-entry, 20-round tournament took about 0.03 s in plain Python). Both are benchmarks, not checks that fail the build.
- If the season page misses its guideline, the fallback is to store final places when a tournament finishes and recompute them on corrections (BR-112).

**Alternatives considered.** Persisting derived data and recalculating it on every write (faster reads, more code and the risk of drift). Field assignments derived on read from result times (needs a stored log of field changes and placements by hand, and moves a match being played when an earlier result is corrected).

## ADR-010 — Lots: stored seed and SHA-256 ordering

**Status.** Proposed.

**Context.** The PRD decides by lot in many places: the league ranking (BR-020), random shuffle (BR-022), DYP halves and partners (BR-032, BR-033), sit-outs (BR-058, BR-063), strict order among tied entries (BR-074) and *Lord have mercy* (BR-084). Because standings are computed on read (ADR-009), a lot inside a computation must come out the same on every read.

**Decision.**
- Every tournament gets a random 128-bit seed, generated with `secrets` when it is created and stored. The seed never changes.
- A lot orders the candidates by `SHA-256(seed ‖ purpose ‖ id)`, where `purpose` names the use (for example `dyp-partner:2`, `tiebreak`, `sit-out:round-4`) and `id` is the candidate's stable UUID. A random draw (shuffle, partner draw, *Lord have mercy*) is the same ordering applied to the candidates.
- **Draws are stored as data and never silently re-drawn.** The seeding shuffle (BR-022) and the DYP halves and partners (BR-032, BR-033) are drawn in setup, shown to the organizer and stored. The organizer can then reorder the seeds by hand (FR-034) or set the DYP halves by hand (FR-033, BR-032); drawn DYP pairs themselves are not edited by hand, only re-drawn. Draws made while generating or adding a round (sit-outs, *Lord have mercy*) are stored with the matches.
- A new draw happens when the organizer asks for one ("shuffle again", "new DYP draw", and in Doubles "pair the rest", which pairs the players without a partner by the lot `doubles-pair:<n>`) or when the entries change in setup. Every new draw increments a stored draw counter that is part of `purpose`, so it differs from the old one and is still reproducible.
- **Changing the entries in setup.** Any change to the entries after seeds or draws exist (adding or removing a player or pair, changing a pair's members, a new DYP draw) discards the seeding, whether drawn or computed from the league ranking, any hand reordering of seeds, and for DYP the halves computed from the ranking with their partners. Hand-set DYP halves and Doubles pairs are the organizer's decisions and are kept; the changed player is added to or removed from them. Where the inputs are complete (shuffle, ranking seeds, ranking halves), the app draws again in the same transaction; where the organizer must complete them first (hand-set halves), generating (FR-035) waits until the draw exists. The app warns before anything is discarded. Monster DYP draws nothing in setup, and the organizer's top-player marks are kept.
- Going back to setup (FR-036, FR-046) keeps the existing draws while the entries are unchanged. If entries were added while the tournament was in progress (late entries, BR-045, BR-054, BR-067), the seeding and draws are made again as above, with the warning. Going back to setup also clears every entry's disabled flag, since disabling exists only while rounds are played (FR-044). After the tournament has started, late entries and disabling never redraw anything.
- Only lots inside computed standings (BR-020, BR-074) are re-evaluated on read, and they always give the same answer for the same seed. The league ranking's final lot (BR-020) uses the tournament's seed with the purpose `league-ranking`: every use of the ranking (seeding, DYP halves, the Monster DYP grouping and its top players) happens inside a tournament, so tied players are drawn afresh for each tournament instead of keeping one order all season.
- **The reschedule (BR-054) draws no lot.** The reschedule after a late entry is a **deterministic construction** that prefers BR-054's seven criteria in their order; the last two, the late entry's opponents and then the other matches compared round by round with the better seeds first, are a fixed order instead of a lot, so the reschedule has no `purpose` and no draw counter. At large sizes the seven criteria are the construction's order of preference, not a searched optimum. The construction is defined with issue #62. The Python engine produces fixture files of the construction's results, and the TypeScript demo is tested against them, so both give the same schedule. The reschedule is stored with the matches and not computed again.
- **Several late entries (BR-054).** Entries added in one step are fitted in one after another, in league-ranking order (BR-020, BR-021 for pairs), each by the reschedule for one late entry, so the order of picking does not matter and the construction needs no case for several entries. The reschedules of one step are stored in one transaction, so the organizer and the viewers see the schedule change once. Entries added in separate steps get one reschedule each, in the order added.
- The tie lot of BR-074 includes the number of completed rounds in its `purpose` (e.g. `tiebreak:after-round-3`). Without it, the same two tied entries would be ordered the same way all tournament long; with it, the order is stable on every read but drawn afresh after each round.

**Consequences.** Results are reproducible in tests and do not depend on the Python version. Python's `random` module is not used: ruff's `banned-api` rule bans it in the whole backend and the engine's import-linter contract (ADR-009) forbids it, so every lint run checks it without a test of its own. The organizer loses a hand reordering of seeds whenever the entries change in setup, which the warning tells them; in exchange the rule is the same for every tournament type.

**Alternatives considered.** A stored seed with `random.Random` (its sequence is not guaranteed to stay the same across Python versions). Storing every lot outcome (tie groups change with every result, which conflicts with computing on read). Redrawing only what a change invalidates (keeps hand reorders and stable shuffles, but every type and input needs its own rule, and a ranking-based DYP changes completely anyway). A season seed for the league ranking's lot (the same tied player would win every lot all season).

## ADR-011 — Pairing when a repeat cannot be avoided

**Status.** Proposed.

**Context.** Swiss must not repeat an opponent "while it can be avoided" (BR-057), and Monster DYP must not repeat a partner "while it can be avoided" with the grouping changed "as little as needed" (BR-062). The PRD does not say what happens when a repeat cannot be avoided, and the simple "play the next entry down" rule (BR-056) can paint itself into a corner at the bottom of the standings.

**Decision.**
- **Swiss: BR-056 first, a whole-field matching as the fallback.**
  - Before pairing, the engine removes the entry that sits out (BR-058) and disabled entries (BR-064), so an even number of entries remains. Round 1 is paired by BR-055 and needs no search; with an odd number of entries the lowest seed sits out (BR-058), since before any result the seeds are the standing. From round 2 the sit-out is chosen by BR-058: entries that did not sit out the round before first, then the fewest sit-outs (a missed round counts as one, BR-064, BR-067), then the one whose sitting out leaves the fewest repeat opponents in the round, then the lowest place, then a lot. A direct implementation of the repeat-opponent key pairs the round once per candidate. A large field needs no such search: when n ≥ 2r + 2 (below), every candidate leaves a pairing without a repeat, so all candidates are level on the key and the engine skips it. Only a small field, where a repeat can be forced, pairs the round once per candidate, and a small field pairs fast, so the round stays within the 1-second target (Timing).
  - From round 2, the engine applies BR-056 as written: top-down, each unpaired entry plays the next entry below it that it has not played. If that completes, it is the result.
  - If BR-056 gets stuck (the last entries have all played each other), the engine re-pairs the whole field with a minimum-weight perfect matching, solved with the blossom algorithm (`networkx.min_weight_matching`, which finds a minimum-weight matching among those of maximum cardinality). The weight of a pair is the squared difference of the two entries' positions in the standing, counted among the entries that play the round, times the number of entries at or below the upper one, so the top of the standing is kept first ("1st v 2nd") when a pairing without repeats allows it, and pairings stay close to the standings and a sit-out or a disabled entry between two entries does not push them apart. First only pairs that have not met are used, with edges limited to entries within 16 of those positions; if that has no perfect matching, the window is doubled (32, 64, …) up to the whole field. Only if the whole field has no repeat-free perfect matching are pairs that have met added. Their cost ranks a matching by three keys in turn: first the fewest pairs that have met (BR-057 counts repeated opponents, so one pair that met twice beats two pairs that met once each), then the fewest earlier meetings among those pairs (a pair that met once beats a pair that met twice), then the position cost above. Each key's weight is a whole number above the most the later keys can add up to over a whole matching, derived from the field size and the history, so the order holds for any field size.
  - Because the matching works on the whole field, it may change pairs anywhere in the standings, not only at the bottom. A wider window is used only when a narrower one has no perfect matching, so the result is repeat-free but not necessarily the cheapest pairing overall.
  - A repeat can be forced only in a small field. Let n be the even number of entries playing the round after the sit-out and disabled entries are removed, and r the number of rounds already generated. Each entry has met at most r opponents, so it has at least n − 1 − r unplayed opponents among the n. If n ≥ 2r + 2, that is at least n/2, and by Dirac's theorem the unplayed pairs contain a Hamiltonian cycle and therefore a perfect matching. The bound is sufficient, not necessary.
- **Monster DYP: swaps first, a matching when they get stuck.** The engine starts from the BR-060/BR-061 grouping, read as a row of places in which group g holds places 4g to 4g + 3 and its 1st and 4th partner its 2nd and 3rd. While a team repeats a partnership, it swaps the two players whose exchange leaves the fewest repeated teams; of those, the swap that leaves the smallest sum of earlier counts (how many times each team has been partners before, so a pair that has partnered twice is avoided before one that has partnered once); of those, the swap that moves the players least far from their BR-060 places, so neighbours come first; and of those, the first by the lot `monster-swap:round-<n>` (ADR-010). A swap may stay inside a group, which changes only the partners: with a single group (4 to 7 players) no other swap exists. The swaps stop when no repeat is left or none improves the draw. If repeats are left, the same minimum-cost matching as in Swiss (`engine/matching.py`, networkx) tells whether a better draw exists: it matches all the players, a pair that has not partnered costs 0, and a pair that has costs more than all the sums of counts together, plus the number of times it has partnered, so the matching has the fewest repeated teams and, of those, the smallest sum of earlier counts; among equal matchings it keeps the most teams as they stand. If it is better, its teams replace the others, each placed where its players move least. Every round therefore has the fewest repeated partners possible, whatever the size of the field, and of those the smallest sum of earlier counts. In rounds 1 and 2 top players are never swapped, so they stay in different groups (BR-061), and each is the 1st of its group, as in BR-061's example, so partners the group's 4th. There the swaps alone remove every repeat: each player has had at most one partner, so swapping the non-top player of a repeated team with a player who is not a top player in another team leaves both new teams without a repeat. The matching therefore runs only from round 3. The top players of such a round are chosen after the sit-outs (BR-063): the first M playing players, where M is the round's number of matches, taking players marked by the organizer first and then the others in league-ranking order. A top player who sits out or is disabled is replaced by the next one, so every group has exactly one even when a disabled or late player changes the number of matches. This is BR-061 and FR-041: when more players are marked than a later round has matches, the marked players who play count in league-ranking order, and top players are not exempt from the sit-out lot, since they are picked after the sit-outs (BR-061, BR-063). The sit-outs themselves follow BR-063: players who did not sit out the round before are picked first, then the fewest sit-outs (a missed round counts as one, BR-064, BR-067), then a lot. The engine still takes the exemption, the order of the marked players and the rule about the round before as parameters, with the rule off by default; the PRD has the first two fixed and the third always on, and issue #60 makes the engine follow it. "As little as possible" is measured as the sum of how far each player moved from their BR-060 place. Repeated opponents are allowed. The placement is not guaranteed to move players least at any size, because the greedy swaps and the placement of the matching's teams can move players more than needed; the number of repeats is always the minimum.
- The Swiss matching graph is built in standing order, so the result is the same for the same standings. Ties between equally good Monster DYP swaps are broken by lot (ADR-010).
- **Timing.** Measured locally for 256 entries after 19 rounds, the window-16 step takes 0.1 to 0.2 seconds and handled every simulated case, although BR-056 got stuck in 7 to 11 of the 20 rounds of a simulated 256-entry tournament, almost every round from about round 13; for large fields the fallback is the normal path. Each doubling of the window costs about twice as much, and the whole field alone takes 1.3 to 1.8 seconds, so the worst case takes several seconds. The target of 1 second per round for 256 entries applies to the window-16 step; a benchmark records it and does not fail the build. The engine of P12 (`engine/swiss.py`) draws 64 entries over 7 rounds in about 0.02 seconds, which a benchmark test bounds at 1 second (marked `benchmark`, skipped by the default `pytest` and CI, run with `pytest -m benchmark`), and a simulated 256-entry tournament of 20 rounds in about 2 seconds, at most 0.21 seconds per round (both in the dev container).

**Consequences.**
- Swiss: a test checks that the result equals the BR-056 pairing whenever BR-056 completes. A property test (ADR-012) checks that no repeat occurs whenever a repeat-free perfect matching exists, with a maximum-cardinality matching on the unplayed pairs (or brute force below 12 entries) as the oracle. Hypothesis sizes are capped at about 32 entries and run with `deadline=None`, since a whole-field solve for 64 entries already takes about 0.6 seconds and Hypothesis's default deadline is 200 ms per example.
- Monster DYP: property tests play whole simulated tournaments and compare each draw's repeated teams and sum of earlier counts with a brute-force minimum for up to 14 players, check that no repeat occurs while Dirac's bound n ≥ 2r + 2 holds for up to 24 players, and check the rules of BR-060–BR-063 (including exactly one top player per group in rounds 1 and 2, as its 1st). Measured locally for 256 players over 20 rounds, a draw takes at most 0.6 seconds; the swaps resolved every round there, and the matching ran only in small fields late in the tournament.
- If the heuristic produces visibly bad rounds in practice, it can be replaced without changing anything outside the engine.

**Alternatives considered.** BR-056 with backtracking from the bottom of the standings (much faster and keeps the top pairs unless forced, but needs a search budget and the matching as a further fallback). A window-limited matching that allows repeat edges from the start (picks a repeat whenever the window permits one, even when a repeat-free pairing exists outside it).

## ADR-012 — Quality gates in GitHub Actions

**Status.** Proposed.

**Context.** The repository is on GitHub. Mistakes in brackets or points are exactly what would make a group go back to paper. The repository is private on GitHub Free, where branch protection, required checks and rulesets are not available for private repositories (the rulesets API answers "Upgrade to GitHub Pro or make this repository public").

**Decision.** Every pull request runs these checks in GitHub Actions. On GitHub Free they are required by agreement: changes reach `main` only through a pull request with passing checks and a review, and nothing in GitHub enforces it.

| Area | Checks |
|---|---|
| Backend | `ruff` (lint and format), `mypy --strict`, import-linter, `pytest` under `coverage` (100 % in the engine; 90 % overall from the first feature), `hypothesis` property tests for the engine, integration tests against a real PostgreSQL service container, pytest-alembic's migration tests, `alembic upgrade head` and `alembic check`, OpenAPI drift check (ADR-008), `uv audit` |
| Frontend | ESLint, Prettier, `tsc --build` over the app, `vite.config.ts` and the Playwright tests (`pnpm typecheck`), against the types generated from the committed OpenAPI schema, Vitest with Testing Library, `i18next-cli lint` (no user-facing text outside `t()` and `<Trans>`), `pnpm audit --prod` (known vulnerabilities in the production dependencies) |
| End to end | Playwright (ADR-013) |

- Jobs are filtered by the changed paths inside the workflow: each job is skipped when its area did not change, and one aggregate job (`ci-ok`) fails if any job it depends on failed. Documentation-only pull requests then skip the heavy jobs, and the checks keep reporting once they become required. A workflow-level `paths` filter would leave a required check waiting forever.
- The backend job's PostgreSQL 17 service is created with the built-in locale through `POSTGRES_INITDB_ARGS` (ADR-002, DATA-MODEL §2), since the test of the `lower()` folding fails without it. It holds three databases: one for the integration tests, one that pytest-alembic's tests empty before each test, and one for `alembic upgrade head` and `alembic check`.
- The drift check exports the schema with `python -W error -m tourneyhub.openapi`, which also fails on a duplicate operation id, and compares it with the committed `backend/openapi.json`. `uv audit` reports known vulnerabilities in the locked dependencies; it is still a preview command (`--preview-features audit-command`).
- The worked examples in the PRD (§5.1 and the examples inside BR-054, BR-055, BR-058, BR-061, BR-063, BR-081, BR-111) are test vectors the engine must reproduce exactly. §5.2 step 2 ("the 3 best-ranked of the 12 who play are in different matches") holds for every seed: top players are not exempt from the sit-out lot, and they are picked after the sit-outs, from the players who play (BR-061, BR-063; per the review of #46).
- Property tests cover invariants such as: no bye against a bye (BR-041), seeds 1 and 2 meet only in the final (BR-042), every round-robin pair meets exactly once or twice (BR-050), in a round robin without late entries every entry sits out equally often (BR-051), in Swiss and Monster DYP the sit-out counts of entries present and enabled since round 1 differ by at most one (BR-058, BR-063), shared places skip numbering correctly (BR-104).

**Consequences.** On GitHub Free the budget is 2,000 Actions minutes a month and 500 MB of storage shared by Actions artifacts and packages; container images in GHCR are currently free, with at least a month's notice of any change. Playwright artifacts are therefore kept for 7 days and videos only on failure (ADR-013). Before the pilot, the owner of the repository decides again between GitHub Pro (required checks in private repositories, more minutes and storage) and a public repository (required checks and Actions minutes free, code and documents public).

**Alternatives considered.** GitHub Pro now (checks enforced, paid by the owner of the repository). A public repository now (everything free, everything public).

## ADR-013 — End-to-end tests and checks with Playwright

**Status.** Proposed.

**Context.** The MVP succeeds when a real group plays whole evenings on a phone (PRD §1). Unit tests cannot show that the screens, the API and the database work together, or that result entry is quick on a small screen.

**Decision.**
- Playwright tests run against the production images (`compose.prod.yaml`, ADR-004: Caddy, built frontend, API, PostgreSQL), both locally and in CI.
- Browsers are added in stages. Every pull request runs desktop Chromium. Mobile emulation in Chromium (Android) and in WebKit (iPhone Safari) is added before the pilot, since players and organizers mostly use phones.
- Scenarios grow with the features. The first two are the DYP evening from PRD §5.1 and the Monster DYP night from §5.2, end to end, checking the standings and season points the PRD states. The server draws the seed (ADR-010), so the Monster DYP night checks the rules (at most one top player per group among the players of rounds 1 and 2, standings consistent with the results) rather than the exact grouping, which the engine tests cover (ADR-012). Further scenarios follow their features:
  - Sign-up with and without a valid code; login, logout and staying logged in after a reload; password change.
  - The admin flow: setting the sign-up code and resetting an organizer's password, after which the organizer's old login can no longer be refreshed and their next login asks for a new password before anything else (ADR-006).
  - A viewer opening the share link without an account sees the league and cannot change anything; tournaments in setup are hidden (FR-070, FR-072).
  - Switching between English and Czech, and the default language taken from the browser (FR-081).
  - Entering a result in at most three taps from the bracket, schedule or round, plus typing scores (FR-082).
- Accessibility checks with `@axe-core/playwright` run on the main screens, in the light and the dark colour scheme, and produce a report that does not fail the build. They run axe's WCAG 2.0, 2.1 and 2.2 Level A and AA rules (tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`), with `target-size` enabled by name because axe leaves the WCAG 2.2 rules off by default, and its `best-practice` rules. WCAG 2.2 Level AA is the level the report measures and the level the gate requires from RM-11 (Stage 1); the `best-practice` rules stay a report.
- `target-size` checks AA's minimum of 24 × 24 CSS px (SC 2.5.8). The 44 × 44 px of the result-entry controls (FR-082) is the AAA size of SC 2.5.5, chosen because those taps are made on a phone at the table; axe does not check it, so the FR-082 scenario asserts it.
- On failure, CI keeps the trace and screenshots, and the video (`retain-on-failure`), as build artifacts for 7 days (ADR-012).

**Consequences.** Each pull request pays for one browser. Problems specific to WebKit, including how Safari handles the refresh cookie, may surface only when WebKit is added before the pilot.

**Alternatives considered.** Cypress (weaker WebKit support). Visual regression with screenshots (brittle at this stage; can be added later). All three browsers on every pull request from the start (about three times the minutes and artifacts).

## ADR-014 — Deployment: images in GHCR, manual pull on the VPS

**Status.** Proposed.

**Context.** Development happens locally first (ADR-004). The MVP's success test, a real group playing a season and following the share link (PRD §1), needs a public instance, so deployment comes after the MVP features work locally and before the pilot season starts.

**Decision.**
- On a push to `main`, CI builds the two images, `api` and `web` (Caddy with the built frontend), runs Playwright against them, and pushes them to the GitHub Container Registry only if the tests pass. The VPS therefore runs exactly the images that were tested.
- The VPS has `compose.yaml`, `compose.prod.yaml` and a `.env` file with `COMPOSE_FILE=compose.yaml:compose.prod.yaml`, and no source code. Updating means `docker compose pull && docker compose up -d`; migrations run as the `api` container starts.
- GHCR packages stay private. The VPS logs in to GHCR once with a token that can only read packages. Only the last few versions of each image are kept, in case GHCR storage stops being free (ADR-012).
- CI holds no SSH key to the VPS.

**Order.** Local development of the MVP features → deployment to the VPS with HTTPS, backups and basic monitoring → the pilot season. Backups are a precondition for the pilot: losing a season's results would fail the MVP. Before the pilot, the monitoring must alert a person, since a down instance on a tournament evening sends the group back to paper, and the privacy requirements hold, since real names and email addresses of EU residents are stored (PRD §6.11, proposed in #48): the VPS and the backups are hosted in the EU (FR-100) and the "Privacy" page is live (FR-101). Which host, and who is the data controller, the owner decides with the PRD owner.

**Designed in that phase.** Backups (scheduled `pg_dump` stored off the VPS, with a tested restore), monitoring and who it alerts, log retention (the api and Caddy's error log already redact share tokens; Caddy's access log, if switched on, needs the same, ADR-008) and secret handling on the VPS. HSTS, once Let's Encrypt works on the real domain: first with a `max-age` of one day, raised to one year after the first automatic renewal; no `includeSubDomains`, no `preload`. The api's own PostgreSQL role: a non-superuser owner of the `tourneyhub` database, created before the VPS database volume first exists; until then the api connects as `postgres`.

**Consequences.** What runs on the VPS is what CI tested. Updating needs a person with access to the VPS, which suits a pilot with one instance.

**Alternatives considered.** Automatic deploy from CI over SSH (CI holds a production key). Building on the VPS (load on production, and what runs is not exactly what CI tested).
