## ADR-001 — Backend: Python, FastAPI, SQLAlchemy, Alembic

**Context.** The owner wants a Python backend serving a separate React frontend. The MVP is a single instance for groups the owner knows: low traffic, one organizer per league, no realtime (PRD §4.2).

**Decision.**

| Concern | Choice |
|---|---|
| Runtime and tooling | Python 3.13, `uv` for environments, the lock file and scripts |
| Web framework | FastAPI on uvicorn |
| Schemas | Pydantic v2; request and response models form the API contract (ADR-008) |
| Database access | SQLAlchemy 2.0 with typed `Mapped[]` models, **synchronous** sessions, psycopg 3 driver |
| Migrations | Alembic, one linear history; autogenerate is only a draft and every migration is reviewed |
| Settings | pydantic-settings, environment variables with the prefix `TOURNEYHUB_`; startup fails on missing or invalid config |
| Password hashing | argon2-cffi (Argon2id) |

**Consequences.**
- Endpoints are plain `def` functions; FastAPI runs them in its thread pool. With the MVP's load this is more than enough, and it avoids async ORM pitfalls (lazy loads across awaits, session sharing).
- Moving to async later is possible endpoint by endpoint if realtime (RM-03) needs it.

**Alternatives considered.** Django with Django Ninja (auth, admin and migrations built in; the owner chose FastAPI). Litestar (smaller ecosystem). Async SQLAlchemy with asyncpg (no benefit at MVP load, more complexity).

## ADR-002 — Database: PostgreSQL

**Context.** The data is strongly relational (leagues, seasons, tournaments, entries, matches) and must be the same in development and production.

**Decision.** PostgreSQL 17, run as a container in docker-compose locally and on the VPS.

**Consequences.**
- Constraints are enforced in the database where they can be: at most one active season per league via a partial unique index; primary keys are UUIDs generated by the application.
- Player names are unique per league ignoring case (BR-001) via a unique index on `(league_id, lower(name))` that **includes removed players**, so two different people never share a name in past results. When the organizer adds a name that belongs to a removed player, the app offers to restore that player with their history instead.

**Alternatives considered.** SQLite (simpler operation, but would need a migration to PostgreSQL once the roadmap's later stages arrive).

## ADR-003 — Frontend: React, Vite, TypeScript, Tailwind, shadcn/ui

**Context.** Every screen must work on a phone, and entering a result takes at most three taps (FR-082). The UI is in English and Czech (FR-080, FR-081).

**Decision.**

| Concern | Choice |
|---|---|
| Framework and build | React 19, Vite, TypeScript in strict mode |
| Styling and components | Tailwind CSS, shadcn/ui (Radix-based components copied into the project) |
| Server state | TanStack Query |
| Routing | React Router |
| Translations | react-i18next; no hard-coded user-facing strings; dates formatted with `Intl` in the chosen language |
| API types | Generated from the backend's OpenAPI schema with `openapi-typescript` (ADR-008) |
| Package manager | npm, lock file committed |

**Consequences.** The design is mobile-first. The knockout options keep their English names in both languages (FR-080). Dark mode (RM-11) can later be added through Tailwind's theme without restructuring components.

**Alternatives considered.** Mantine (faster start, less control over the look). Plain Tailwind (most work, accessibility of dialogs and menus on us).

## ADR-004 — Repository layout and local development in Docker

**Context.** Development happens locally first; deployment to the VPS comes in a later MVP phase (ADR-014).

**Decision.**
- One repository with `backend/` (Python package `tourneyhub`) and `frontend/` (the React app). Root `docker-compose.yml` for local development.
- Local services: `db` (PostgreSQL), `api` (uvicorn with reload, source mounted), `web` (Vite dev server with hot reload). Vite proxies `/api` to `api`, so the browser sees one origin, as in production (ADR-005).
- A second compose file (or profile) builds the production-like stack — `caddy` serving the built frontend and proxying `/api` — for Playwright (ADR-013) and later for the VPS.
- Alembic migrations run when the `api` container starts. A CLI entry point `tourneyhub` hosts admin and maintenance commands (ADR-007).
- Configuration comes from a `.env` file; `.env.example` is committed, `.env` is not.

**Consequences.** One `docker compose up` gives a working app. The same images are used locally and on the VPS.

## ADR-005 — One origin behind Caddy

**Context.** Splitting the frontend and API across domains would need CORS and cross-site cookies.

**Decision.** In production, Caddy is the only public entry point. It obtains HTTPS certificates automatically (Let's Encrypt), serves the built frontend on `/` (falling back to `index.html` for client-side routes) and proxies `/api/*` to the `api` container.

**Consequences.** No CORS configuration. The refresh cookie (ADR-006) is first-party. Only Caddy's ports 80 and 443 are exposed; `api` and `db` are reachable only on the internal Docker network.

**Alternatives considered.** Nginx with certbot (more configuration, separate certificate renewal). Separate domains for app and API (CORS and cookie scoping without benefit).

## ADR-006 — Authentication: JWT access token and rotating refresh token

**Context.** Organizers stay logged in on a device until they log out (FR-003). A password change or an admin password reset must be able to end existing logins (FR-004, FR-006). Only the organizer and admin screens need authentication; viewers use the share link (FR-070).

**Decision.**
- **Passwords:** at least 12 characters (FR-002), hashed with Argon2id; rehashed on login when the parameters change. Email addresses are compared case-insensitively and are unique.
- **Access token:** JWT signed with HS256, valid 15 minutes, carrying the user id, the refresh-token family id and the admin flag. The SPA keeps it in memory only and sends it as `Authorization: Bearer`.
- **Refresh token:** an opaque 256-bit random value, stored only as a SHA-256 hash, sent as an `HttpOnly; Secure; SameSite=Strict` cookie restricted to the path `/api/v1/auth`. Every refresh issues a new refresh token and invalidates the old one (rotation). Reusing an invalidated token revokes the whole family (theft detection).
- **Staying logged in:** refresh tokens expire after 365 days without use, and each refresh restarts that period. An organizer who uses the app stays logged in until they log out; a forgotten device loses access after a year. **This deviates slightly from FR-003** (which has no expiry) and needs the PRD owner's confirmation; if confirmed, FR-003 is amended.
- **Revocation:** logout revokes the current family. A password change revokes every other family of that user. An admin password reset revokes all of them.
- **CSRF:** API calls authenticate with the Bearer header, which a browser never adds by itself. The refresh and logout endpoints, which rely on the cookie, also require a custom request header that cross-site forms cannot send.
- **Abuse limits:** login attempts are limited per email address and per IP address, and sign-up attempts per IP address, to stop guessing passwords and the sign-up code. Counters live in PostgreSQL, so no Redis is needed.

**Consequences.** On page load the SPA calls the refresh endpoint to get an access token. A revoked user loses access within at most 15 minutes. The token design also suits a future phone app (RM-19) and Google sign-in (RM-20).

**Alternatives considered.** A server-side session cookie (simpler and revocation is immediate; the owner chose JWT). Long-lived JWTs without refresh (no revocation).

## ADR-007 — Instance admin: admin flag, admin screens, CLI bootstrap

**Context.** The instance admin sets the sign-up code (FR-005) and sets a new password for an organizer who forgot theirs (FR-006). There is one instance and usually one admin, the person running the VPS.

**Decision.**
- The admin is a normal account with an `is_admin` flag. An admin can also be an organizer with their own leagues.
- The admin section in the React app lets an admin set or change the sign-up code, list organizer accounts and set a new password for one (which revokes their logins, ADR-006). Every admin action is checked on the server and recorded with who did it and when.
- The first admin is created on the server with a one-off CLI command, e.g. `docker compose exec api tourneyhub create-admin --email …`, which prompts for the password. The same CLI can grant the flag to an existing account. No web route can create an admin, so a stranger cannot claim the instance on first start.
- Until a sign-up code is set, sign-up is closed. Changing the code does not affect existing accounts (FR-005).
- Admin rights do not give access to other organizers' leagues (FR-007).

**Alternatives considered.** CLI-only administration (smallest attack surface, less comfortable). A sign-up code in an environment variable (a code change needs a restart).

## ADR-008 — API conventions and generated client types

**Decision.**
- REST with JSON under `/api/v1`. The share-link views are anonymous, read-only routes under `/api/v1/public/{share_token}/…` (FR-070–FR-072); every other route requires authentication.
- Errors return an HTTP status and a body `{"code": "<stable_code>", "detail": …}`. The frontend translates codes into English or Czech; the backend never returns user-facing text.
- The OpenAPI schema is generated by FastAPI, exported to `backend/openapi.json` and committed. CI fails if the committed schema differs from the code. The frontend generates its TypeScript types from that file; hand-written copies of API types are not allowed.
- Share tokens are at least 128 bits of randomness, URL-safe (FR-071).
- Mutating operations on a tournament lock its row (`SELECT … FOR UPDATE`) so that two devices of the same organizer cannot interleave changes such as generating a round while entering a result.

**Alternatives considered.** Hand-written OpenAPI first (doubles the work with FastAPI). GraphQL (no need for the MVP's fixed set of views).

## ADR-009 — Tournament engine as pure functions; derived data computed on read

**Context.** Most of the PRD's complexity is in the business rules (§7): brackets, schedules, Swiss and Monster DYP rounds, tie-breakers, places and season points. The data is small: at most 256 entries and 20 group-phase rounds per tournament (FR-032), a few dozen tournaments per season.

**Decision.**
- The engine is a separate package, `tourneyhub.engine`, made of pure functions over immutable data classes. It does not touch the database, the clock or the network, and has no randomness other than the seed it is given (ADR-010). An import-linter contract enforces that it imports nothing from FastAPI, SQLAlchemy or the rest of the app.
- **Stored:** what the organizer decided or what a draw produced — leagues, players, seasons and their placement points tables, tournaments and their settings, entries and pairs, seeds, top players, disabled and late players, rounds, matches, results and seeds for lots.
- **Computed on every read:** tournament standings, BH1, BH2, score difference, places, season standings and the league ranking. The application loads the stored data, calls the engine and returns the result.
- Generating a bracket, a schedule or a round calls the engine and stores the resulting matches.

**Consequences.**
- Derived data can never get out of step with results. Corrections (BR-112), placement table changes (BR-012) and deleted tournaments need no recalculation step.
- A season keeps its own copy of the placement points table: editing the league's table updates the active season's copy; a closed season's copy no longer changes (BR-012).
- Engine rules are tested directly, without a database, with test names referring to BR IDs.
- If a page gets slow, caching can be added later without changing the engine. A guideline for when to act: the standings of a 256-entry tournament should be computed in under 200 ms.

**Alternatives considered.** Persisting derived data and recalculating it on every write (faster reads, more code and the risk of drift). A mix of both (final places stored on finish).

## ADR-010 — Lots: stored seed and SHA-256 ordering

**Context.** The PRD decides by lot in many places: the league ranking (BR-020), random shuffle (BR-022), DYP halves and partners (BR-032, BR-033), sit-outs (BR-063), strict order among tied entries (BR-074) and *Lord have mercy* (BR-084). Because standings are computed on read (ADR-009), a lot inside a computation must come out the same on every read.

**Decision.**
- Every tournament and every season gets a random 128-bit seed, generated with `secrets` when it is created and stored. The seed never changes.
- A lot orders the candidates by `SHA-256(seed ‖ purpose ‖ id)`, where `purpose` names the use (for example `dyp-partner:2`, `tiebreak`, `sit-out:round-4`) and `id` is the candidate's stable UUID. A random draw — shuffle, partner draw, *Lord have mercy* — is the same ordering applied to the candidates.
- **Draws are stored as data and never silently re-drawn.** The seeding shuffle (BR-022) and the DYP halves and partners (BR-032, BR-033) are drawn in setup, shown to the organizer and stored, so the organizer can adjust them by hand before generating (FR-034). Draws made while generating or adding a round (sit-outs, *Lord have mercy*) are stored with the matches.
- A new draw happens only when the organizer asks for one ("shuffle again", "new DYP draw"). Each request increments a stored draw counter that is part of `purpose`, so the new draw differs from the old one and is still reproducible. Going back to setup (FR-036) keeps the existing draws; changing the player list redraws only what that change invalidates.
- Only lots inside computed standings (BR-020, BR-074) are re-evaluated on read, and they always give the same answer for the same seed. The league ranking's final lot (BR-020) uses the season's seed.

**Consequences.** Results are reproducible in tests and do not depend on the Python version. Python's `random` module is not used in the engine; a test enforces it.

**Alternatives considered.** A stored seed with `random.Random` (its sequence is not guaranteed to stay the same across Python versions). Storing every lot outcome (tie groups change with every result, which conflicts with computing on read).

## ADR-011 — Pairing when a repeat cannot be avoided

**Context.** Swiss must not repeat an opponent "while it can be avoided" (BR-057), and Monster DYP must not repeat a partner "while it can be avoided" with the grouping changed "as little as needed" (BR-062). The PRD does not say what happens when a repeat cannot be avoided, and the simple "play the next entry down" rule (BR-056) can paint itself into a corner at the bottom of the standings.

**Decision.**
- **Swiss: exact, as a minimum-cost perfect matching.** Entries are nodes; every pair that may meet gets a cost. A repeated opponent costs more than any possible sum of the other costs, so the matching avoids repeats whenever it can and otherwise has the fewest. The remaining cost is the distance from the BR-056 order: the difference between the two entries' standing positions, so neighbours are cheapest. The matching is solved with the blossom algorithm (e.g. `networkx.max_weight_matching` on negated costs), which is fast enough for 256 entries.
- **Monster DYP: heuristic.** The engine starts from the BR-060/BR-061 grouping. If it contains repeated partners, it swaps players between groups, preferring swaps between neighbouring standing positions, until no repeat is left or no swap reduces the number of repeats. "As little as possible" is measured as the sum of how far each player moved from their BR-060 position. Repeated opponents are allowed. The result is not guaranteed optimal for large fields.
- Ties between equally good pairings are broken deterministically (ADR-010). Generating a round for 256 entries must take under 1 second.

**Consequences.**
- Swiss: property tests (ADR-012) check that no repeat occurs whenever a repeat-free pairing exists, at every size.
- Monster DYP: the same property is checked exhaustively for small fields (up to 12 players) against a brute-force search; for larger fields, tests check only that the rules of BR-060–BR-063 hold and that repeats do not increase compared with the starting grouping.
- If the heuristic produces visibly bad rounds in practice, it can be replaced without changing anything outside the engine.

## ADR-012 — Quality gates in GitHub Actions

**Context.** The repository is on GitHub. Mistakes in brackets or points are exactly what would make a group go back to paper.

**Decision.** Every pull request runs these checks in GitHub Actions, and `main` accepts only pull requests whose checks pass.

| Area | Checks |
|---|---|
| Backend | `ruff` (lint and format), `mypy --strict`, `pytest`, `hypothesis` property tests for the engine, integration tests against a real PostgreSQL service container, `alembic check`, import-linter, OpenAPI drift check (ADR-008) |
| Frontend | ESLint, Prettier, `tsc --noEmit`, Vitest with Testing Library, type generation drift check |
| End to end | Playwright (ADR-013) |

- The worked examples in the PRD (§5.1, §5.2 and the examples inside BR-055, BR-061, BR-081, BR-111) are test vectors the engine must reproduce exactly.
- Property tests cover invariants such as: no bye against a bye (BR-041), seeds 1 and 2 meet only in the final (BR-042), every round-robin pair meets exactly once or twice (BR-050), sit-outs stay even (BR-051, BR-058, BR-063), shared places skip numbering correctly (BR-104).

## ADR-013 — End-to-end tests and checks with Playwright

**Context.** The MVP succeeds when a real group plays whole evenings on a phone (PRD §1). Unit tests cannot show that the screens, the API and the database work together, or that result entry is quick on a small screen.

**Decision.**
- Playwright tests run against the production-like stack (ADR-004: Caddy, built frontend, API, PostgreSQL), both locally and in CI.
- Browsers: desktop Chromium, plus mobile emulation in Chromium (Android) and WebKit (iPhone Safari), since players and organizers mostly use phones.
- Scenarios that must pass:
  - The DYP evening from PRD §5.1 and the Monster DYP night from §5.2, end to end, checking the standings and season points the PRD states.
  - Sign-up with and without a valid code; login, logout and staying logged in after a reload; password change.
  - The admin flow: setting the sign-up code and resetting an organizer's password, after which their old login stops working.
  - A viewer opening the share link without an account sees the league and cannot change anything; tournaments in setup are hidden (FR-070, FR-072).
  - Switching between English and Czech, and the default language taken from the browser (FR-081).
  - Entering a result in at most three taps from the bracket, schedule or round, plus typing scores (FR-082).
- Accessibility checks with `@axe-core/playwright` run on the main screens; serious and critical violations fail the build.
- On failure, CI keeps the Playwright trace, screenshots and video as build artifacts.

**Alternatives considered.** Cypress (weaker WebKit support). Visual regression with screenshots (brittle at this stage; can be added later).

## ADR-014 — Deployment: images in GHCR, manual pull on the VPS

**Context.** Development happens locally first (ADR-004). The MVP's success test — a real group playing a season and following the share link (PRD §1) — needs a public instance, so deployment comes after the MVP features work locally and before the pilot season starts.

**Decision.**
- After a merge to `main`, CI builds two images — `api`, and `web` (Caddy with the built frontend) — and pushes them to the GitHub Container Registry.
- The VPS has only `docker-compose.yml` and a `.env` file, no source code. Updating means `docker compose pull && docker compose up -d`; migrations run as the `api` container starts.
- CI holds no SSH key to the VPS.

**Order.** Local development of the MVP features → deployment to the VPS with HTTPS, backups and basic monitoring → the pilot season. Backups are a precondition for the pilot: losing a season's results would fail the MVP.

**Designed in that phase.** Backups (scheduled `pg_dump` stored off the VPS, with a tested restore), monitoring, log retention and secret handling on the VPS.

**Alternatives considered.** Automatic deploy from CI over SSH (CI holds a production key). Building on the VPS (load on production, and what runs is not exactly what CI tested).
